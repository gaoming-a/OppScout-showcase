# 工程案例：失败如何推动设计收敛

[项目首页](../README.md) · [文档索引](README.md) · [评测结果](evaluation.md)

以下案例来自实际开发与验收，公开问题、原因、修正和验证边界；不公开内置 Prompt、业务数据或实现源码。

## 1. 超时没有释放实际执行

**问题**：候选分析超时后，外部调用或原 future 仍在运行。如果立即释放容量并发起重试，实际并发会超过配置。

**原因**：把业务上的“超时”误当作执行已经结束。

**处理**：直到原执行真正结束才释放在途容量；单任务异常独立收敛，同一会话拒绝第二条活动回复流。模型请求与流式请求共用进程内并发门。

**验证**：已有 Worker、模型与流式回归覆盖这些边界。进程内门仍不是跨进程全局配额，后者保留为后续 Harness 阶段。

## 2. 锁等待期间，租约可能已经过期

**问题**：Worker 发起写入时租约尚有效，等待数据库行锁后却可能已过期；主机时钟差异还会造成不同进程判断不一致。

**原因**：只在等待锁前检查，或由各主机自行解释租约有效期。

**处理**：采用数据库时钟；拿到业务行锁后再检查 owner、fencing 与有效期，并在同一事务写业务状态及对应控制事实。

**验证**：隔离 PostgreSQL 测试覆盖过期拒绝、冲突回滚与成对事实写入。SQLite 快速合同测试不作为这一业务并发边界的证明。

## 3. 专家蒸馏目标大于实际需求

**问题**：有语料和观察仍反复失败。任务同时要求完整人格维度、复杂证据配对、修订和多轮评测；供应商 Schema 限制、重复 ID 和跨维度引用使合成阶段不断受阻。

**原因**：把“日常对话有稳定风格”扩展成一次性生成完整人格，让模型同时负责内容判断与结构关系正确性。

**处理**：收敛为表达与互动习惯。模型提取可观察行为，程序绑定原文与来源并编译规则；领域知识独立检索。没有足够证据的价值、判断或情绪规则保持未验证。

**验证**：一次真实任务完成草稿登记，八组基线 / 加载后三轮对话通过。仍需人工审核和更多对象、材料及场景验证，不能据此宣称完整人格或稳定成功率。

## 4. 补检做了很多，却没有获得新证据

**问题**：来源发现重复下载正文，补检循环又反复使用已经执行过的查询。同一 URL 的不同前缀还曾被算作两个独立来源。

**原因**：查询列表耗尽、外部下载职责和来源身份没有共同闭合。

**处理**：来源发现只获取结果元信息，正文交给来源读取器；使用十个不同查询方向并设置独立尝试上限；按规范化 URL 计算来源独立性。

**验证**：修正后的任务完成九次有界补检，取得符合覆盖门的独立来源。来源不足的任务会明确阻断，不能靠增加同源片段凑覆盖率。

## 5. 语料中的故事进入了无关回答

**问题**：专家把语料中的具体数字、比喻和个人故事带入新的情绪或决策场景，甚至给用户已经确定的题设添加风险标准。

**原因**：原文观察和审计证据直接进入回复上下文，模型把表达风格当成了可复用事实及判断规则。

**处理**：运行时只使用可迁移表达和互动规则，审计原文留在资产证据中；事实来自经范围授权的知识上下文。身份、范围、事实授权和用户题设优先于风格。

**验证**：最终指定任务的题设保持、越界拒答和语料隔离检查通过。这是指定用例的验收，仍需独立人工与泛化评测。

## 6. 指标名称会改变结论

**问题**：容易把 Hit@50、来源组覆盖、条件精确率和一次全链耗时都写成“准确率”或“效率提升”。

**处理**：分别报告已知来源召回、人工相关性、证据准入、真实任务完成和回归；保留样本、日期、分母、排序损失及延迟。

**验证**：公开评测摘要保留 RRF 的 MRR 下降和 CPU 重排 P95 58.988 秒；500-query 与 36-query 两套标签不相互替代。最新 CI 未实际执行时，也不沿用历史全绿结论。
